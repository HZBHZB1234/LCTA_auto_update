# 02 — 建立直连模型的 AI 执行层

> 执行计划，尚未实施。前置：01。下一步：[03 持久工作图](03-durable-work-graph.md)。

## 任务目的

完全解除 translatekit 对模型能力、提示词、异常和配置的控制。让研究员、译者、编辑和裁决者都通过项目自有的执行层工作。

默认协议是 OpenAI 兼容 Chat Completions，使用通用 HTTP 客户端直接发送请求；不再引入一个新翻译包装库来替代旧包装库。

## 需要做什么

1. 建立模型端点目录，记录地址、模型、凭据引用、可支持的任务和已验证能力，而非“翻译服务名称”目录。
2. 定义统一 AI 作业：角色、任务目标、可用证据、输出要求、工具权限、预算和结果归属。
3. 直接实现请求、响应、流式完成判定、错误分类、取消、重试和调用追踪。
4. 将供应商差异隔离在有限的协议配置里；上层协作不处理某家服务的私有异常。
5. 为需要结构化结果的角色提供服务端约束与本地校验；不支持严格 schema 的端点必须显式走兼容方案并完整验收。
6. 建立角色—模型能力评测，保证调度选择依据真实任务表现而非标价和宣传。
7. 删除对 TranslatorBase、TKitConfig、动态修改 translator prompt、translatekit 日志控制和服务注册表的依赖。最终退役在 14 一并验证。

## 要新增的功能

- **结构化 AI 作业执行**：研究报告、候选文本、反例案件和编辑提案都能得到明确归属。
- **能力协商**：验证支持的消息角色、工具调用、结构化输出、流式和参数；“接口兼容”不当作“功能全兼容”。
- **可追踪调用**：保存发送内容、实际模型、结果、使用量和终止原因；密钥不进日志。
- **请求预算与取消**：任务过时或依赖失效后停止继续消耗，迟到结果不能提交。
- **服务级恢复**：针对限流和暂时故障恢复连接，区别于模型内容不合格后的重写。
- **受控工具执行**：AI 可以申请查资料、看相邻原文和查实体；宿主检查权限后执行。
- **可回放替身**：离线使用保存的响应验证调度，不为每次工程检查调用模型。

## 请求与结果边界

基础请求形状使用 `POST /v1/chat/completions` 的 `model` 和 `messages`。工具与 `response_format` 等可选能力按实际端点验证后启用。

收到 HTTP 成功不等于任务完成：截断、拒绝、空结果、未完成工具调用、非法结构和错误引用都必须区分。流式中间内容不能提前成为可交付译文。

结构化输出保证的是形状，不能证明译法正确。不得用“JSON 能解析”代替语义核验，也不得默默更换模型来掩盖质量问题。

OpenAI 官方的 Responses 与 Chat Completions 是不同接口；本阶段不要求第三方兼容端点支持 Responses。若以后接入，作为独立协议适配并评估，不改变统一作业语义。

## Jev 的位置

不原样搬迁已有 Jev 阶段 0。先用新执行层承载有限判定角色；当评测证明 Jev 在某类判断有效时，允许新增独立 HTTP 判定插件。

Jev 不是自由译文生成器，也不能提升术语来源资格。它的专用协议不能被错误地包装成支持全部 OpenAI 协作能力。

## 交付与完成标准

- 新进程不安装、不导入 translatekit，也能完成研究、翻译、结构化审查三种作业。
- 切换端点不要求改写编辑部的角色和任务图。
- 部分流式结果、超时与限流恢复不会重复提交或将半份结果标成功。
- 降级模型、放宽结构要求、增加预算都必须可见；必要能力缺失可延期，不能偷偷降低翻译标准。

## 协议依据

参考 OpenAI 的 [Chat Completions 创建接口](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)、[流式事件](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)和[结构化输出指南](https://developers.openai.com/api/docs/guides/structured-outputs)。

本次通过文档检索取得这些官方页面的内容片段；直接页面抓取受到站点访问限制。未调用真实模型端点，未据此承诺第三方兼容服务的功能、价格或限制，实施时仍须能力测试。
