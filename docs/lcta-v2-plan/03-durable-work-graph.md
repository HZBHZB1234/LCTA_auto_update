# 03 — 建立持久工作图、事件与共享工作区

> 执行计划，尚未实施。前置：01–02。下一步：[04 三语理解](04-trilingual-understanding.md)。

## 任务目的

把一次脚本执行改造成可以研究、等待、追加工作、恢复和重新规划的编辑任务系统。

本任务建设运行机制；任务 08 再加入一致性优先的智能调度策略。不要一开始把两者混成一个不可解释的“总 Agent”。

## 需要做什么

1. 统一接收原文、LLC commit、正式中文发布、知识修订和质量发现等事件，保留来源身份与内容版本；外部纠错可作为可选输入，不成为运行前置。
2. 将研究、对齐、定约、起草、审查、裁决、修订与发布准备表达成不同任务类型。
3. 为每个任务明确输入、依赖、允许写出的成果和完成条件；任务成功是成果通过验收，不是 API 返回成功。
4. 建立版本化共享工作区，保存引用、语义说明、翻译契约、候选、案件和决定。
5. 支持 AI 提议追加研究/审查任务，由程序验证依赖、权限、资源上限后接入工作图。
6. 使过时输入能够使后续任务失效；正在执行的旧任务即使随后返回，也不能覆盖新决定。
7. 完成断点恢复、并发提交、失败重试、任务取消和长期待决问题的持久化。

## 要新增的功能

- **事件去重**：原文 token 相同但中文内容更新仍然是新事件。
- **依赖屏障**：共同契约没有就绪时，下游翻译等待，而不是各自猜一版。
- **作业状态**：等待依赖、可执行、执行中、自动补证、待自动审查、等待新证据、合格、失效、取消和失败能够区分；没有必须人审的状态。
- **成果版本**：同一场景多个候选并存，不用“最后写入的正文”覆盖全部历史。
- **任务恢复**：进程退出、CI 重启和服务中断后恢复实际工作，不重新消费已验收成果。
- **有限动态展开**：限制自动追加任务的深度和总工作量，阻止研究任务无限繁殖。
- **自动唤醒登记**：等待项绑定相关实体、来源、版本和恢复条件，后续有效事件到来自动重入工作图。
- **运行解释**：能够回答某任务为什么在等、为什么重做、谁依赖它。

## 共享与并发原则

共享的是有版本的成果，不是所有 Agent 可随时改写的全局字典。读任务固定输入版本；提交时检查其依赖仍有效。决定变化生成新版本和失效事件。

执行权、结果提交权与知识批准权分开。Agent 提出一个权威词条修改，不等于获得修改权威库的权限。

模型请求可能在网络故障下重复计费，不能承诺远程调用绝对一次。运行时必须保证结果接纳、决定提交和发布效果不重复。

循环依赖须被显式检测：将互相依赖的新实体/场景交给联合研究任务，或升级为待决案件，不能让队列永远互等。

## 初期部署形态

先实现一个可持久化、可恢复的进程级运行时，支持 CI 和本地工作；不要为了“多 Agent”先搭建复杂分布式平台。

存储需承受新进程恢复，Actions cache 只能加速，不能是唯一状态。将来有必要分布式执行时，工作图、成果版本与提交规则保持不变。

## 交付与完成标准

- 运行一个包含“研究→补证→翻译→审查→修订”的动态任务，重启后从正确位置继续。
- 两个角色并发修改同一决定时，不出现无声覆盖。
- 权威事件中途到来可以使相关结果失效，其他无关工作继续。
- 不再用“这个文件翻译成功”作为全部任务类型共同的状态模型。
