# LCTA v2 顺序执行计划

> 所有文件均为未来任务计划，尚未实施。先读[纲领](../lcta-v2-manifesto.md)，再读[总体方案](../lcta-v2-overview.md)。
>
> 这里按默认执行顺序组织，每个编号是一项可独立安排、审阅和验收的建设任务。编号不是一次提交的大小，也不要求先把整个平台做完才能验证某个能力。

全流程以无人值守为硬性产品要求：自动获取 LLC commit、整理知识、翻译、审校、延期恢复和发布；不设置人工审批前置。关键证据不足时自动延期并等待可验证的新证据，不能为了全自动而降低错翻防线。

## 四个可见里程碑

1. **新执行系统可工作（01–03）**：一个角色直接调用模型，任务可以中断恢复，结果归属明确。
2. **AI 可以共同理解和约定（04–07）**：自动消费 LLC 提交，给定一组跨文件内容，产出三语理解、权威知识及共同翻译契约，仍未要求全量自动翻译。
3. **AI 可以完成一致的编辑任务（08–11）**：从研究到联合起草、发现矛盾、修订、定稿，完成一个真实一致性域。
4. **替代旧系统持续运行（12–14）**：无人值守处理提交、中文迟到、长期工作、自恢复和自动交付，删除旧生产路径。

每个里程碑都要能演示端到端结果。避免只交付框架目录、Agent 名称或没有使用者的数据模型。

## 执行纪律

- 每个任务先确认成果对象和使用者，再决定具体模块、框架和存储；计划不要求机械落实某个类名。
- 质量样例从 01 起贯穿每个任务；不要等到 11 才检测错翻、到 14 才有测试。
- AI 协作是待建设产品的能力，不等于开发时必须启动多个助手。
- 可以独立开发明确无耦合的子项，但语义/术语/契约未就绪的任务不能提前起草再补上下文。
- 每项任务都保留“未确定/未通过”的结果；不把流程走完当质量达标。
- 对旧模块采用“迁入已验证能力，删除旧组织方式”的原则。没有价值的兼容层不建。
- 实施过程中可以细化或调整顺序，但不得用节省成本、赶工或追求表面一致性绕过原意检查。
