# 05 — LLC 提交采集、知识整理与自动术语体系

> 执行计划，尚未实施。前置：04。下一步：[06 AI 编辑部](06-ai-editorial-collaboration.md)。

## 任务目的

建立自动工作的权威资料编辑部：从 LLC 仓库的 commit 中读取实际改动，理解它修改了哪些名称、称呼和规则，核验后持续维护项目自己的术语与作品知识。旧词表停更不再影响运行，也不需要维护者逐条整理。

采集与整理本身可完全自动化；证据不足的条目进入自动待证流程，不能为了无人值守而把机器创造的中文当作权威。

## 需要做什么

1. 建立 LLC 仓库的持续读取能力，跟踪可信分支、提交关系、发布标签和正式发布资产；无需上游授予 webhook 管理权，定时读取即可完整工作。
2. 首次启动自动建立内容基线，并分批回溯有效历史；后续按已处理提交增量获取。历史研究可在后台推进，不阻塞已有明确证据的内容。
3. 自动获取变更前后文件，按稳定字段身份识别新增、补译、修订、删除、重命名、回滚与仅格式调整。提交说明提供线索，具体文件内容决定事实。
4. 将变化关联到 KR/JP/EN、实体和场景。不能仅因中文和原文出现在同一 commit，就认定它们是同一语义版本。
5. 由 AI 资料研究员整理新词、别名、称呼、范围、机制表达和改译关系；由确定性检查与独立语义核验确认引用和解释。
6. 自动把通过来源、版本、语义与冲突核验的材料编译为词条、权威句对与作品知识，并产生可被调度器消费的知识变更事件。
7. 将旧静态词表作为待核验导入材料，自动检索权威依据、拆分义项和范围；覆盖不足保持可见，不要求先人工清洗整张表。
8. 支持资料撤回、实体拆分、权威冲突与新证据重评。每次知识变更可定位其证据与受影响内容，不用全局字符串替换传播结论。

## 提交采集必须具备的能力

### 连续、完整、可恢复

保存已经发现的提交与已经完成处理的提交两个进度，先持久记录事件，再推进处理；失败任务留在待处理队列，不能因为分支头前进就被跳过。

按提交拓扑和稳定 SHA 处理历史，不能按提交标题日期猜顺序。支持分页、合并提交、文件重命名、删除、回滚和分支历史改写；历史不再连续时重新建立可核对的基线，标记受影响旧结论失效，不把旧进度强接到新历史。

GitHub 返回的补丁或文件列表可能不完整。采集器需发现缺页与截断，必要时读取指定 SHA 的完整文件、树或只读 Git 对象；不能把一页结果当作全部变化。瞬时失败与限流自动退避重试，恢复后补齐遗漏。

### 从代码差异整理翻译知识

自动形成字段级“之前是什么、现在是什么、涉及谁、适用哪个版本”的事实，再由 AI 分析其含义。格式化、数组重排和文件移动不应被误解为改译。

每个整理结果包含可定位的原文、中文及变化证据。模型提到的中文必须确实存在于引用材料，身份与含义还需核验；“这是中文”或“提交写了修复”都不足以证明某一术语对应成立。

可自动整理的成果包括实体和别名、三语对应、中文权威形式、称呼关系、机制措辞、版本修订与撤回关系。对抽取时新创造的别名或中文表达，只保留提案身份。

### commit 与正式权威的关系

提交被收录不等于所有内容已正式认可。区分“观察到的上游改动”“已核验的原文事实”“已获正式来源确认的中文”。只根据可信来源、发布状态、实际内容对应和适用范围自动转换资格，不用模型置信分替代来源。

未发布提交可提前用于发现问题和研究变化，待正式中文或可靠发布映射出现后自动确认；不需要人工点击。正式发布比源码更新时，从资产直接整理权威并保留资产身份，不捏造不存在的 commit 来源。

源码和发布资产存在差异时分别保存；只有实际内容吻合或可验证的构建来源支持时才建立对应。标签指向 `main` 并不证明该标签的 ZIP 内容与 `main` 相同。

## 新格式应表达什么

| 内容 | 必须解决的问题 |
|---|---|
| 稳定实体与义项 | 同一 KR 字符串不能唯一决定对象 |
| KR/JP/EN 名称与别名 | 别名同指不等于所有称呼都应译成全名 |
| 中文形式与来源资格 | 正式权威、待确认上游中文、项目机器候选明确区分 |
| 范围与反例 | 人物义/普通词义、剧情/技能、不同组织语境可以不同 |
| 证据定位 | 仓库、commit、路径、字段、前后内容；发布资产另有内容身份 |
| 源文与发布对应 | 记录语义版本和对应依据，不能只保存抓取时间 |
| 工作状态 | 已核验、待证、冲突、弃用、候选及自动恢复条件 |
| 历史与依赖 | 为什么改、取代哪条、哪些稿件和知识受影响 |

建议使用一实体一份可读 YAML/JSON 文档，配独立证据和提案存储，运行时编译为只读视图。格式应适合机器自动更新、版本比较和人工阅读；具体字段在本任务中定稿，不继承旧三列词表的表达限制。

例如旧记录“피주머니 → 血袋(间章名词)/血囊(BUFF译名)”应拆成不同范围的证据绑定，而非要求每次翻译都解释斜线文本。此例来自旧调查，不表示已重新确认其当前权威译法。

## 要新增的功能

- **LLC 历史与增量采集器**：自动拉取 commit、完整正文、相关原文和发布资料，支持断点及历史变化。
- **变更知识整理员**：从字段变化发现术语、称呼、机制与旧理解的变化，产出带引用的提案。
- **自动核验与入库**：依来源资格、对应关系、原文含义与反例检查决定接纳，不设人工审批环节。
- **自主维护词库**：自动拆义、链接别名、限定范围、拒绝无依据候选并在新证据到来时重评。
- **权威翻译记忆与知识视图**：以版本发布可复用内容，运行任务不读取半份新词表。
- **来源与冲突追踪**：可查看一个译名在哪个提交出现、是否正式发布、为什么取代旧形式。
- **提案隔离与自动待证**：项目机译名称不能因多次采用、多模型认同或进入发布包就升级为权威。

## 交付与完成标准

系统从空知识库启动，可自动建立基线、消费后续提交、对齐三语与中文、整理词条并编译可用知识；期间无需手工整理或批准。至少展示同形多义、多语别名、场景限定译名、权威改名与撤回各一例。

覆盖分页/补丁不全、格式重排、合并与回滚、历史改写、来源不明中文以及源码落后于 Release 等情况。失败后不漏提交、不重复生效，不把不匹配版本强行对齐。

普通词表、角色资料、效果表、翻译记忆、例句和摘要均须遵守来源资格。无人值守运行时，正常材料自动入库，有疑点材料自动补证或延期，不能让“自动通过”成为来源污染的入口。
