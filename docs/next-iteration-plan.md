# 下一个大迭代方向分析

> 本文基于对 `src/`、`tools/`、`tests/` 的代码通读，以及对 `benchmark/runs/` 三次真实运行产物的
> 逐条取证（含 `translation-dump.jsonl` 中的 API 调用原文）。所有结论均标注了可复核的证据来源。

---

## 0. 结论速览

**当前系统的主要瓶颈不是"模型不够聪明"，而是"工程可靠性与评测信噪比"。**

| 判断 | 结论 |
| --- | --- |
| 翻译核心（`translateFunc`）的**架构设计** | 成熟，无需重构 |
| 最大单点损失 | **22 次 504 网关超时**直接导致文件产不出，而非翻译质量问题 |
| 消歧层（stage_0）的**有效性** | **实测有效**，判断正确（见 §2.2 原文取证） |
| 提示词层（"四色次元"事故） | 消歧判断**正确但未被下游尊重**，是链路耦合缺陷，不是"模型不认识这个词" |
| 评测信噪比 | **不足**：同代码两次运行差 0.348 chrF，`stage0_degraded` 在 run 间漂移 1→2→6 个文件 |
| **引入向量库** | **当前不是好方案**，是"用大炮打蚊子"，且解决不了主要瓶颈（详见 §4） |

---

## 1. 项目现状：边界清晰的双层结构

`docs/architecture.md` 声明的边界被代码严格遵守：

- `src/translateFunc/` —— 从 LCTA 工具箱**原样同步**的翻译核心（含 `processor.py` 2119 行、
  `builder/prompt.py` 1254 行、`builder/request.py` 502 行）。不承载任何 GitHub/版本逻辑。
- `src/auto_update/` —— 本项目适配层（配置、网络、解包、幂等、版本、打包、编排）。
- `tools/status_server/` —— 自托管状态服务（Flask，轮询 Steam/steamcmd → 提取 CDN token → dispatch）。
- `.github/workflows/check.yml` —— 仅装配 Python、跑入口、发 Release、传诊断包。

**这个分层是资产**：任何迭代都应当继续把"翻译智能"留在 `translateFunc`，
把"工程/编排/评测"放在外层，避免再次污染翻译核心（`README.md` 末尾明确要求）。

### 1.1 关键实现事实（后续方案的前提）

1. **术语表规模有硬上限**：`src/translateFunc/get_proper.py` 最多拉 10 页 × 800 = **8000 条**，
   超出直接抛 `RuntimeError`；工作缓存实测 **2000 条**（`benchmark/cache/proper_terms_paratranz.json`）。
2. **术语匹配是纯 AC 自动机精确子串匹配**（`matcher/ac_automaton.py`，`matcher/engine.py`），
   共 4 个自动机：专名 / 角色 / 状态效果 ID / 状态效果名。**没有模糊匹配、没有语义召回**。
3. **无任何向量/嵌入基础设施**：全仓库（排除 `.venv`、`tools/steamCmd`）grep
   `embedding|vector|faiss|chroma|milvus|qdrant|sentence-transformer|cosine` **零命中**；
   `requirements.txt` 仅 5 行，无 numpy。
4. **单文件请求规模很小**：实测 `baseline-01` 中 26 个成功文件共 **158 个文本块**，
   平均每文件 **~6 块**，单文件引用术语数多为 **2–16 条**（最大 20）。

## 2. 实测诊断：钱丢在哪里

以 `benchmark/runs/baseline-01`（33 文件 / 898 字段）为样本。

### 2.1 主要损失 = 基础设施失败，不是翻译质量

```
overall.mean_chrf_nontrivial = 27.912
missing_fields = 247      (27.5% 的字段压根没产出)
zero_fields    = 405      (45.1% 的字段 chrF=0)
files_produced = 30 / 33
```

**647/898 = 72% 的字段要么缺失要么得零分。** 追查 `SAVE_ERROR` 根因：

```
SAVE_ERROR 计数(全量 dump) = 22
唯一 reason = "服务器内部错误: 504 - <html>...504 Gateway Time-out...alb</html>"
```

**22 次失败全部是同一个原因：DeepSeek 网关 504。** 按 `processor.py:225-234`，
`_translate()` 抛出的任何异常都被归入 `SAVE_ERROR` 并**直接终止该文件**，该文件全部字段归零。

> 这是**收益最高、改动最小**的一处：504/429/5xx 属于**可重试的瞬时故障**，
> 与"翻译逻辑错误"应区别对待。当前却被一视同仁地判为致命错误。

另按 file_type 看，`STORY` 类 87 个字段 **mean_chrf = 0.0、missing = 87**（全军覆没），
同样源于 3 个 story 文件（`P10116.json`、`PersonalityVoiceDlg/...`、
`BattleAnnouncerDlg/Announcer_MatthiasKira_51.json`）落在 `SAVE_ERROR` 名单里。

### 2.2 消歧层实际是有效的 —— 原文取证

流传的说法是"模型把 `사색` 读成地支'巳'所以译错"。**实测证据否定了这个归因。**

在 `baseline-01` 的 dump 中，包含 `사색 차원` / `四色次元` 文本块的那次 stage_0 调用，
模型返回（原文摘录）：

```json
{
  "term": "사",
  "applies": false,
  "actual_meaning": "사색(四色)的构词成分，意为'四'",
  "reason": "Block3'사색 차원'(四色次元)中사是'四色'一词的组成部分（汉宁土辰相关概念），
             并非黑兽十二分支的地支'巳'，且此处无汉字标注蛇/巳的混淆问题"
}
```

模型**完全正确地**识别出这是"四色"而非"巳"，并主动否掉了术语 `사 → 巳`。

进一步核对三次运行的实际产出：

| run | `FourDimensionYisang.name` 实际输出 | 判定 |
| --- | --- | --- |
| `baseline-01` | **四色次元** | ✅ 正确 |
| `subval-base` | **四色次元** | ✅ 正确 |
| `subval-iter-01` | **巳色次元** | ❌ 回归 |

**结论**：`baseline-01` 是**对的**。`巳色次元` 是 `subval-iter-01` 这次**提示词改动引入的回归**，
不是基线缺陷。`compare.md` 把这条列为"变差 -68.06"，准确含义是
**"本次改动把本来正确的 四色 改坏了"** —— 这是一个**回归信号**，而且是有价值的信号。

这条同时暴露了真正的产品级缺陷（见 §2.4）：**消歧结论没有被下游强制尊重**。

### 2.3 评测信噪比不足

| run | mean_chrf_nontrivial | exact_rate | missing | 产出文件 | stage0_degraded |
| --- | --- | --- | --- | --- | --- |
| `baseline-01` | 27.912 | 7.52 | 247 | 30/33 | 1 个 |
| `subval-base` | 50.149 | 21.053 | 0 | 26/26 | 2 个 |
| `subval-iter-01` | 49.801 | 20.395 | 0 | 26/26 | **6 个** |

三个问题：

1. **口径不可比**：`baseline-01` 分母含 247 个"缺失计零"字段（`notes` 明示
   `hyp_missing_counts_as_zero: true`），`subval-*` 是 0 缺失。跨 run 直接比 mean_chrf 是**错的**。
2. **同代码重跑就有噪声**：`subval-base → subval-iter-01` 的"无混杂共同字段"口径 Δ = **-0.348**，
   而 `compare.md` 自己写明 `|Δ| ≤ 0.5 视为无信号（端点噪声）` —— 即**这次改动的效果落在噪声里，
   无法判定**。
3. **混杂源在漂移**：`stage0_degraded_files` 从 2 个变成 6 个（stage_0 调用失败被静默跳过）。
   这会让 105 条字段"不可用于归因"，而它本身是**非确定性的**。

> 含义：当前流水线**没有能力可靠地判断一次提示词改动是好是坏**。
> 在这个前提下优化提示词，等于在噪声里调参。

### 2.4 已确认的结构性缺陷（按价值排序）

| # | 缺陷 | 证据 | 影响 |
| --- | --- | --- | --- |
| D1 | 瞬时网络故障（504）被判为致命，文件整体丢弃 | 22 次 SAVE_ERROR 全为 504 | **最大单点损失**，~27% 字段 |
| D2 | 消歧结论仅通过"删除术语"表达，无强约束 | §2.2 取证 | 消歧对了也可能被下游覆盖（巳色回归） |
| D3 | 不存在跨文件术语一致性机制 | 各文件独立翻译，无全局术语状态 | 同一韩文词在不同文件可能译法不一 |
| D4 | 术语召回纯精确子串，短术语（≤2 字 532/2000）大量误触发 | `proper.py:32` `is_short` 已承认此问题 | 无谓消歧调用，稀释 prompt |
| D5 | `_apply_disambiguation` 按整词删除，无法表达"此块不适用、彼块适用" | `processor.py:1712-1750` | 粒度太粗 |
| D6 | 术语/角色/affects 全靠 AC 精确匹配，无形态学处理 | `engine.py:123-140` | 韩文助词/变体导致漏召回 |
| D7 | 评测 harness 源码不在仓库内 | `benchmark/` 被 `.gitignore:16` 整体忽略，仅剩 `.pyc` | **评测能力不可复现、CI 不可用** |

**D7 特别值得强调**：`bench_lib.py`、`run_e2e.py`、`score_e2e.py`、`build_update_dataset.py`
的 `.py` 源码**不在版本控制内**（`git ls-files benchmark` 为空），只有 `__pycache__` 里的 `.pyc`。
评测是这个项目唯一的质量反馈回路，却是**唯一没有纳入版本管理的部分**。

## 3. 计划：三个候选迭代方向

### 计划 A —— "可靠性 / 止血"迭代（推荐作为**下一个小迭代**）

**目标**：把已经产出的质量**真正交付出去**，不追求新能力。

范围：
1. **错误分类 + 瞬时故障重试**（D1）
   - 在 `_translate` 的异常处理中区分：`HTTP 5xx / 429 / timeout / 连接错误`（可重试）
     vs `JSON 解码 / 结构不匹配 / 配置错误`（致命）。
   - 瞬时故障按指数退避重试（尊重 `Retry-After`），并把该 part 标记为 `deferred`
     而非让整个文件归零；重试耗尽后走既有降级阶梯，最后才回退 KR 原文。
   - 结构化 `failure_kind` 落进 `processing_log.jsonl` / `run-summary.json`，便于统计。
2. **CI 健康门禁**：`features.enabled` / 失败文件数 / 缺失字段数写入 `run-summary.json`，
   在 Release 说明中显式列出"本次有 N 个文件因基础设施失败未产出"。
3. **评测 harness 入库**（D7）：把 `benchmark/` 的 `.py` 源码从 `.gitignore` 移出（保留
   `runs/`、`updates/`、`cache/` 等产物的忽略），使评测可复现、可进 CI。

**判定标准**：`baseline-01` 复跑，`missing_fields` 从 247 → 接近 0，`files_produced` 33/33。

**风险**：低。这是纯工程改动，可完全用现有 benchmark 验证。

---

### 计划 B —— "一致性 / 术语闭环"迭代（推荐作为**真正的下一个大迭代**）

**目标**：解决"翻译对了词形，但跨文件不一致 / 消歧结论不被尊重"。

范围：
1. **消歧结论硬化**（D2/D5）
   - stage_0 的 `actual_meaning` 目前只用于"删除术语"，信息被丢弃。
   - 改为：把 `applies=false` 的术语降级为**块级负向约束**（`<do_not_apply>`），
     而不是从术语表移除整词；使"此块不适用"能精确表达。
2. **全局术语一致性表**（D3）
   - 运行期维护 `KR 词 → 已定译名` 的全局字典（跨文件共享，`MatcherEngine` 已是天然的汇点）。
   - 同一 KR 词第二次出现时，把**运行内已定译名**作为强约束注入，
     避免同词异译；并输出"术语一致性报告"。
3. **术语召回改进**（D4/D6）
   - 短术语加**词边界/形态学**约束（韩文助词剥离），降低误触发；
   - 对长术语保留子串匹配（AC 自动机已经很快，无需替换）。
4. **术语基建扩容**：`get_proper.py` 的 10 页上限改为可配置分页直至取尽（D 类小修）。

**判定标准**：新增"术语一致性"指标（同一 KR 词在全量产出中的译名唯一率）。
**风险**：中。会改到 `translateFunc`，需遵守"上游同步"约定，改动尽量做在外围可插拔层。

---

### 计划 C —— "评测科学化"迭代（**前置投资，建议与 A 并行**）

**目标**：让"改动是否变好"这个问题可以被可靠回答。

范围：
1. **同一配置重复运行**：对同一 dataset 跑 N=3 次，报告 Δ 的**均值与极差**，
   而不是单次 Δ。`compare.md` 已经写了这个要求，但没有工具支持。
2. **消除/显式化混杂**：把 `stage0_degraded_files` 从"静默跳过"改为**失败即重试**，
   或至少在评分时把受影响字段**从分母剔除并单独报告**，而不是让它们污染归因。
3. **统一口径**：跨 run 比较前强制对齐字段集合；`missing` 字段单独成桶，不混进 mean_chrf。
4. **回归门禁**：把"已正确的高价值用例"（如 `四色次元`）固化为**回归用例集**，
   任何改动若打破它则告警 —— 这正是 `subval-iter-01` 本应被拦住的地方。

**判定标准**：给定一次改动，能输出"chrF Δ = x ± y（N=3），是否越过噪声带"的明确结论。
**风险**：低，但需要**真实的 API 预算**（重复运行 = 成本 × N）。

## 4. 专题：引入向量库是不是一个好方案？

### 4.1 结论

**当前不是。** 向量库解决的是"大规模、语义模糊、开放域"的召回问题；
而本项目当前的瓶颈是"22 次 504 超时"和"评测噪声"。**引入向量库不会让这两个数字变好。**

### 4.2 逐条论证

**(1) 没有"大规模召回"问题需要解决**

- 术语表实测 2000 条（硬上限 8000），**平均每个文件只引用 2–16 条术语**（实测最大 20）。
- 单文件请求平均 ~6 个文本块。
- 现状是**精确 AC 自动机**，构建 O(L)、搜索 O(m+k)，在这个量级上**已是常数级开销**。
- 用 ANN 索引（HNSW/IVF）去替代一个在 2000 条模式上跑得飞快的 AC 自动机，
  **是性能上的倒退**（还要加嵌入推理延迟 + 索引维护 + 模型下载）。

**(2) 目标问题不是"语义相似"，而是"精确对应 + 形态变体"**

翻译术语的核心需求是：给定韩文原文里的某个片段，**确定地**找出它的既定译名。
- 这是**精确匹配/形态归一化**问题（`사색` vs `사`，助词剥离），
  **不是**"这段话和哪段话语义相近"。
- 向量召回**天然会引入假阳性**：`사`（巳）与 `사색`（四色）在嵌入空间里可能很近，
  这恰恰是**我们想避免**的错误方向。
- §2.2 已经证明：**当前模型自己就能正确判断语境**。缺的不是"更聪明的召回"，
  而是"消歧结论被下游尊重"（计划 B-1）。

**(3) 现有"上下文"机制已覆盖检索要做的事**

`ProperAnalyzer.analyze()` + `extract_contexts_batch()` 已经做了：
对每个术语，**扫描全部 KR/JP/EN 游戏文件**，收集最多 20 条真实用例
（含 JP/EN 平行句），并用 `compute_confidence()` 做 Jaccard 相似度判定。
- 也就是说：**"检索术语的真实使用语境"这件事已经实现了**，且是基于**确定性全文扫描**，
  在离线阶段一次完成。
- 换成向量库做同样的事，收益不明、复杂度上升。

**(4) 成本与工程负担是真实且不对称的**

引入向量库意味着：嵌入模型选型与体积、CPU 推理延迟、索引构建/版本化/持久化、
依赖增加（numpy/faiss/chroma）、CI 时间上升、以及**离线构建产物的分发问题**
（GitHub Actions 每次跑都要重建索引）。
而它换来的收益在当前数据规模下**接近零**。

**(5) 它与主要瓶颈完全正交**

| 瓶颈 | 向量库能解决吗 |
| --- | --- |
| 22 次 504 导致文件归零 | ❌ 完全无关 |
| 评测信噪比不足 | ❌ 完全无关 |
| 消歧结论未被尊重（巳色回归） | ❌ 无关（这是控制流问题） |
| 跨文件术语不一致 | ❌ 无关（这是运行期状态问题） |
| 短术语误触发 | ⚠️ 可能边际改善，但词边界规则更便宜、更可控 |

### 4.3 什么情况下**应该**重新考虑向量库

给出明确的触发条件，避免这条结论被误读为"永远不要用"：

1. **术语表规模跨过 ~5 万条**，且 AC 自动机构建/内存成为实测瓶颈（需先有 profile 证据）。
2. **出现"译法检索"需求**：例如"这句中文历史上是怎么译的"——即**翻译记忆库（TM）**。
   注意：**TM 是向量库的合理场景**，因为它本质是"句子级语义近邻检索"，
   与"术语精确对应"是两回事。
3. **出现"用户反馈/人工修订回流"闭环**，需要按语义找相似历史修订。
4. **术语表不再是 KR→CN 一对一字典型**，而是需要"多义 + 语境选择"的软匹配 ——
   但即便如此，也应**先证明规则/小模型方案不够用**。

> 一句话：**先把 504 修好、把评测做可信、把消歧结论接上；等到真的出现
> 万级以上的语义检索需求、（届时）再用数据决定是否上向量库。**
> 现在上，是在噪声里增加一个不可验证的复杂组件。

### 4.4 如果确实想做"检索增强"，一个更划算的中间形态

不引入向量库，但可以显著增强"上下文供给"：

- **翻译记忆（TM）轻量版**：用 `LLC_zh-CN` 熟肉本身构建 `KR 句 → CN 句` 的**哈希/前缀索引**
  （确定性、零依赖），在翻译时把"本句在历史版本中的既有译法"作为参考注入。
  这对"上游改了一个字"的场景极其有效，且完全可解释。
- **术语共现聚类**：用现有 AC 自动机统计术语共现，做**规则级**的"这几条术语常一起出现"
  提示，成本近零。
- 这两者都**不需要**嵌入模型，且**可被现有 benchmark 直接验证**。

## 5. 推荐路线

```
下一个小迭代  →  计划 A（止血：504 重试 + 门禁 + harness 入库）
并行          →  计划 C（评测科学化：N 次重复 + 混杂显式化 + 回归用例）
下一个大迭代  →  计划 B（一致性闭环：消歧硬化 + 全局术语表 + 形态学召回）
暂缓          →  向量库（等 §4.3 触发条件出现；优先试 §4.4 轻量 TM）
```

**理由**：A 的投入产出比最高且立即见效（~27% 字段止损）；C 是让 B 能被验证的前提
（否则 B 的改动落在噪声里，重蹈 `subval-iter-01` 的覆辙）；B 才是真正的能力跃迁。
向量库在 A/B/C 完成前都是**过早优化**。
