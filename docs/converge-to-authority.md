# 让译文向权威译文收敛：结构性改造方案

> **范围声明**：本文**不考虑** bug 修复与 benchmark 指标。
> 问题只有一个：**在不改 bug 的前提下，做什么结构性改造，能让产出越来越像 LLC 官方熟肉？**
>
> 所有数字均来自对 `benchmark/updates/2026072401`（一份真实的上游更新快照，含
> `raw-kr`/`raw-jp`/`raw-en` 生肉与 `llc-base`/`llc-latest` 两份官方熟肉）的实测。

---

## 0. 核心论点

当前系统是一个**从零翻译**的系统：拿到韩文，靠提示词 + 术语表，让模型现场写中文。

但项目手上其实握着一座金矿 —— **23.5 万条已对齐的官方译文**：

```
raw-kr 文件数 2073 / 20.6 MB
llc-latest 文件数 2048 / 19.4 MB   ← LLC 官方熟肉，即"权威译文"的答案
```

**实测对齐质量：**

| 层级 | 实测结果 |
| --- | --- |
| 文件名（去掉 `KR_` 前缀） | **2037 / 2048 = 99.5%** 一一对应 |
| 条目 id | **91291 条** KR 条目有同 id 的中文对应；2030/2037 个文件 **100% 对齐** |
| 字段路径 + 字符串值 | **234,897 个字段**存在对齐中文；**对齐率 99.99%**（仅 22 个 KR 独有字段） |

> 也就是说：**这个游戏几乎每一句韩文，都已经有一句官方中文摆在磁盘上，
> 而且能通过 `文件路径 + 字段路径` 零歧义地配对。**

**当前架构完全没用上这个事实。** 每次运行都把它当作"上次的参考译文"（`llc_path`），
只在**判定是否已翻译**时用一下（`_check_translated`），翻译时**从不检索**它。

**结构性结论**：从「**生成**（generation）」转向「**检索 + 校验 + 兜底生成**（retrieval-first）」，
是让译文向权威收敛的**唯一杠杆足够大的方向**。下面给出具体形态。

---

## 1. 为什么"检索优先"在这个项目上特别成立

一般机器翻译场景里，"检索优先"未必划算。但这个项目有三个特殊条件，使它的收益极大：

### 条件一：真实更新是**极小增量**

实测 `llc-base → llc-latest`（相邻两次官方发布）的字段级差异：

```
官方中文总字段       234,646
与上一版完全相同     232,249  (98.98%)
被修订（同路径改值）   1,529  ( 0.65%)
全新字段路径             868  ( 0.37%)
```

**一次更新里真正的新内容只有 0.37%，且 99% 的存量译文与上一版逐字相同。**

而当前流水线的做法是：把 KR 全量扫一遍，按**字段级覆盖率**决定哪些要翻
（`_get_translating`，见 MEMORY.md 约定 1）。虽然它确实会跳过已覆盖字段，
但**没有覆盖到的字段仍然靠模型重新生成**，而不是去找"同一句话在别处的官方译法"。

### 条件二：游戏文本**高度重复**，同一韩文句在多个文件反复出现

这是 Limbus 这类游戏的固有特征：同一个 buff 描述、同一句技能文案，
会出现在 `Skills_*`、`Passives*`、`Bufs*`、`EGOgift_*`、各 `-{chapter}` 变体文件里。
实测证据（`subval-iter-01/compare.md`）中大量 case 是**同一句被重复翻译**：

```
UserTicket-EGOBg.json::79::desc   ┐
UserTicket-L.json::79::desc       ├─ 三份文件、同一条描述，译文应完全一致
UserTicket-R.json::79::desc       ┘
```

当前架构下，这三份是**三次独立的模型调用**，得到三个可能不同的结果。

### 条件三：权威译文**就是同一套 schema 的同一批文件**

不需要对齐不同格式、不同切分。`llc-latest/BattleKeywords.json` 与
`raw-kr/KR_BattleKeywords.json` 是**同结构镜像**，字段路径直接可比。

> 三个条件叠加的结论：**"先查官方怎么说，查不到才让模型写"，
> 在本项目里命中率极高、实现成本极低、且结果天然与权威一致。**

---

## 2. 方案总览

```
                    ┌─────────────────────────────────────┐
                    │  L0  权威语料索引（离线构建，入库）  │
                    │  文件路径+字段路径 → 官方中文        │
                    └──────────────┬──────────────────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
  ┌───────────┐            ┌─────────────┐            ┌──────────────┐
  │ P1 精确命中│            │ P2 同句复用 │            │ P3 术语共识  │
  │ path 级查表│            │ KR 值指纹   │            │ 官方译名挖掘 │
  └─────┬─────┘            └──────┬──────┘            └──────┬───────┘
        │                         │                          │
        └────────────┬────────────┴──────────────┬───────────┘
                     ▼                           ▼
            ┌─────────────────┐         ┌──────────────────┐
            │ 剩余未命中 → LLM │         │ 术语/风格约束强化 │
            └─────────────────┘         └──────────────────┘
```

三条检索通路**互不依赖、可独立上线**，按投入产出比排序为 **P1 → P3 → P2**。

## 3. P1：路径级权威查表（最高优先级）

### 3.1 机制

构建一张映射表：

```
key   = (KR 文件相对路径, 字段路径元组)
value = 官方中文文本
```

翻译时，对每个待翻字段：

1. 先查该表；
2. **命中** → 直接采用官方译文，**不调用模型**；
3. **未命中** → 进入现有 LLM 流程。

### 3.2 为什么它是对的

- 实测该表在一次更新后**命中率可达 98.98%**（存量未改动部分）。
- 命中即**逐字等于权威译文**，chrF = 100，**这是收敛的上界**。
- 它是**确定性**的：同样的输入永远得到同样的输出，消除 run 间抖动。
- 它把 LLM 预算集中到真正的新内容上（0.37% 新字段 + 0.65% 修订）。

### 3.3 与现有设计的自然契合

`processor.py` 已有 `_check_translated()` → `_get_translating()` 的**字段级覆盖率判定**
（MEMORY.md 约定 1 特意强调过必须在字段路径粒度）。P1 本质是**把这个判定从"跳过"
升级为"回填"**：

- 现在：字段已被 LLC 覆盖 → 跳过（依赖 `_de_get_translating_text` 用 LLC 回填）；
- 改造后：字段未覆盖，但**在权威语料的其他位置有同源译文** → 也能回填。

> 注意一个**已被验证的坑**：`_de_get_translating_text` 的组裝必须以 KR 结构为骨架
> （MEMORY.md 约定 3）。P1 的回填必须走同一套骨架逻辑，不能另起一套"整条替换"，
> 否则会丢掉 KR 该条目内的结构性变化。

### 3.4 需要想清楚的一点

"权威语料"应当取**哪个版本**？建议：

- 以**当前 Release 的熟肉**（`cooked_repository` 最新正式 Release 的资产）为权威源；
- 每次运行**重建索引**（234K 字段，纯字符串操作，秒级）；
- 索引**不入库**（可以从熟肉随时重建），只有**构建逻辑**入库。

## 4. P3：从官方译文反向挖掘术语共识（次高优先级）

### 4.1 观察到的问题

当前术语表来自 **paratranz 众包**（`get_proper.py`，实测 2000 条，硬上限 8000）。
但这些术语是**人写的建议**，未必等于**官方最终采用的译名**。

成熟做法是：**从已有官方平行语料中统计出"官方实际怎么译这个词"**，
用它来**校准/覆盖**众包术语表。这比任何提示词工程都更直接地逼近权威。

### 4.2 机制

对每条术语 `(KR term → 建议译名)`：

1. 在平行语料中找出所有**包含该 KR term 的字段对** `(kr_text, cn_text)`；
2. 检查 `cn_text` 中**是否实际出现了建议译名**；
3. 统计命中率：
   - 高命中 → 该术语是可靠的，**提升为强约束**；
   - 低命中 / 译名从未出现 → 说明**官方用的是别的词**，从高频片段中挖掘候选；
4. 产出**术语置信度表** + **官方译名候选表**。

### 4.3 为什么这能显著改变结果

回到那个著名的 `四色` 案例。术语表里有：

```
사 → 巳   (note: 黑兽分支。有时括号注释的汉字会误给出蛇，以韩文原文的用词(读音)为准。)
```

这条术语**本身就是一个陷阱**：它把 1 个音节的 `사` 硬绑到"巳"。
而实测中 stage_0 消歧**正确识别出**这是"四色次元"（JP `四色次元`、EN `Quadricolor Dimensions`），
但当它生效时输出 `四色次元`（正确），失效时输出 `巳色次元`。

**如果引入 P3**：统计 `사` 这个 term 在 234K 官方字段里的实际译法，
会发现 `사` 绝大多数情况下**并不译作"巳"**，从而**自动降低该术语的权重**，
甚至把它标记为"高误触发风险词"。这是**数据驱动的、可复现的**修正，
而不是靠人再写一条 note。

### 4.4 附带收益：解决短术语误触发

实测术语表里 **532/2000 条是 ≤2 字符**（`len 1: 34, len 2: 498`）。
`proper.py:32` 的 `is_short` 已承认这是问题。P3 的统计天然给出每个短词的
**实际歧义度**，可以据此对短词施加更严格的匹配约束（词边界 / 需要伴生词）。

## 5. P2：值级指纹复用（处理"同句多文件"）

### 5.1 机制

以 **KR 文本值本身**（归一化后）为键，而不是以路径为键：

```
key   = normalized(kr_text)        # 去空白/标点归一化
value = 官方中文译文（取最高频 or 最新）
```

路径级查表（P1）**覆盖不到**的场景，它来兜：

- 同一句出现在**新文件**里（新版本新增了文件，路径没历史）；
- 同一句出现在**不同字段路径**下（上游重构了 schema）；
- 该句在官方语料中**已存在**但当前路径是新增的。

### 5.2 实测价值

这是一个**纯确定性、零依赖**的复用层。配合 §1 条件二（游戏文本高度重复），
它能把"同句译法不一致"从根上消除 —— 同一句 KR 永远得到同一句中文。

### 5.3 关于"相似但不相同"

这里有一个**刻意的保守设计**：P2 只做**精确值匹配**（归一化后完全相等），
**不做语义相似检索**。理由是：

- 语义相似会引入**假阳性**（把"差不多"的句子套用成"就是这个"）；
- 而假阳性在**术语/技能文本**里是**灾难性**的（数值、条件、层数错一个就错）；
- 真正的相似句已经是**新内容**，交给 LLM 更安全。

> 这一条同时回答了"要不要上向量库"：**在 P1/P2/P3 这个框架里，不需要。**
> 详见 §7。

## 6. 配套的结构性改造（让上面三条真正生效）

### 6.1 术语从"全局单表"变为"分层 + 带证据"

当前 `MatcherEngine.build_proper()` 接收一张**扁平术语表**，所有术语地位相同。
建议改为**分层结构**：

| 层级 | 来源 | 约束力 |
| --- | --- | --- |
| **L1 官方实证** | P3 从平行语料统计出的高置信译名 | 强约束（必须使用） |
| **L2 众包术语** | paratranz | 建议（可被消歧否决） |
| **L3 模型学习** | `proper_learned.json`（现有 `new_terms` 回流） | 弱建议 |

这样 `사 → 巳` 会落在 L2，而 P3 统计出的"사 在四色语境下不译巳"会形成
**L1 级别的语境化证据**，消歧决策就有了**可依赖的证据层级**，
而不是让模型在 prompt 里"自己判断"。

> 注意与 MEMORY.md 约定 6 的一致性：现有 `merge_terms()` 是"**远程优先**"。
> 分层后，优先级应变成 **L1（官方实证）> L2（远程众包）> L3（本地学习）**，
> 即**引入一个比远程表更高的权威层**，而不是推翻"远程优先"。

### 6.2 把"消歧结论"变成一等公民

当前 `_apply_disambiguation` 只能做一件事：把 `applies=false` 的术语
**从术语表里整条删掉**（`processor.py:1712-1750`）。信息丢失严重。

stage_0 的返回其实很丰富：

```json
{"term": "사", "applies": false,
 "actual_meaning": "사색(四色)的构词成分，意为'四'",
 "reason": "..."}
```

`actual_meaning` 是一个**极有价值的信号**，但完全没被下游使用。
建议结构改为：

- 消歧结果**按文本块**记录（而不只是全局删词）；
- `actual_meaning` 注入 stage_1，作为该块的**正向提示**（"此处 사 意为'四'"）；
- 形成**块级术语约束**，而非全局术语开关。

这直接对应"粒度太粗"的问题：现在的模型是"要么整条术语用，要么整条术语不用"，
无法表达"这个词在此块是 A 义、在彼块是 B 义"。

### 6.3 跨文件一致性：把 `MatcherEngine` 升级为运行期术语账本

`MatcherEngine` 已经是天然的全运行共享点（`pipeline.py` 里创建一次，
传给所有 `FileProcessor`）。建议让它承担**运行内术语一致性账本**：

- 记录"本运行中 `KR 词 → 首次采用的译名`"；
- 该词再次出现时，把首次译名作为约束注入；
- 运行结束输出**术语一致性报告**（同词异译清单）。

这是**纯增量**改造，不改变现有调用契约，且对 WorkerPool 并发安全
（现有 `_proper_lock` + 原子替换引用的模式可直接沿用）。

### 6.4 风格对齐：把 `translate_doc.py` 从"静态手册"变为"动态风格样本"

当前 `SKILL_DOC`（94 行）与 `ROLE_STYLE`（15 个角色）是**人工编写的静态指南**。
它们描述的是规则（"正面效果用获得"、"堂吉诃德自称吾"）。

但**官方译文本身就是最好的风格样本**。建议：

- 用 P1/P2 索引，为**每类文本**（skill / story / UI）抽取**官方的真实句对**
  作为 few-shot 示例；
- 对**角色**：`RLOE_COMPARE` 已能把韩文角色名映射到 `ROLE_STYLE`。
  可以进一步从官方语料里**抽出该角色的真实台词**作为风格锚点，
  替代（或补充）人写的"语言风格"描述。

这样风格约束从**规则描述**升级为**实证样本**，与权威译文的贴合度会显著提高。

## 7. 回到"向量库"：在这个新框架下它处于什么位置

在 §3–§6 的框架里，**向量库依然不是当前该做的事**，理由变得更清晰了：

1. **P1/P2/P3 全部是确定性精确匹配**，命中率由实测支撑（99.99% 字段对齐、
   98.98% 跨版本不变）。它们在**不需要嵌入模型**的前提下，直接把大部分字段
   锚定到权威译文。
2. 真正需要"语义相似"的，只剩**0.37% 的新字段**。为这 0.37% 引入
   嵌入模型 + ANN 索引 + 依赖链，**投入产出严重失衡**。
3. 更关键的是**风险方向相反**：P1/P2 的错误模式是"查不到 → 交给 LLM"（安全），
   而向量召回的错误模式是"查到个差不多的 → 套用"（危险）。
   在数值/条件/层数敏感的文本里，后者不可接受。

**什么时候该重新考虑向量库**（明确触发条件）：

- 需要**跨语言语义检索**来做"这句中文历史上怎么译的"（即真正的**翻译记忆 TM**），
  且精确指纹命中率已证明不足（需要先有实测数据）；
- 术语/语料规模跨过**十万级**且实测到索引瓶颈；
- 引入**人工修订回流**，需要按语义找相似历史决策。

> 结论：**先把 P1 做出来，用实测命中率说话。**
> 如果 P1+P2 的精确命中率已经能覆盖 99% 的字段，向量库就没有存在必要；
> 如果不达预期，那时再谈 —— 而且届时会有**真实数据**支撑决策。

## 8. 落地顺序与预期

| 阶段 | 内容 | 依赖 | 预期效果 |
| --- | --- | --- | --- |
| **S1** | L0 索引构建 + P1 路径级查表 | 无 | 存量字段**逐字等于**权威译文 |
| **S2** | P3 官方术语挖掘 + 术语分层 | S1 语料 | 术语向官方实际用法收敛 |
| **S3** | P2 值级指纹复用 | S1 | 消除同句多文件译法分裂 |
| **S4** | 6.2 消歧升级为块级约束 | 无（可并行） | 恢复 `actual_meaning` 的价值 |
| **S5** | 6.3 运行期术语账本 | 无（可并行） | 跨文件一致性 |
| **S6** | 6.4 动态风格样本 | S1 语料 | 风格向官方样本对齐 |

**S1 是单点最关键改造**：它把"生成"变成"查表 + 生成"，
且完全可以用现有语料**离线验证命中率**，不需要调 API、不需要跑 benchmark。

## 9. 需要你确认的设计决策

1. **权威源以哪个为准？** 当前 Release 的熟肉，还是本地累积的最新 LLC？
   （关系到索引时效性与"官方修订"能否被吸收）
2. **P1 命中的字段是否允许被 LLM 覆盖？** 建议**默认不允许**（权威优先），
   但保留开关，用于处理"官方译文本身有误/术语与当前版本不符"的情况。
3. **索引重建时机**：每文件处理前一次性重建（全局），还是按需懒加载？
   （234K 字段纯字符串操作，全局重建更简单，建议全局）
